# Tango Done&Go V3：六项待审决策

> **历史资料说明（2026-10-16）**：本文件保留 V3 方向决策、差距讨论与待审问题，不代表当前探戈 Done&Go 已采用的产品架构、入口或上线承诺。当前唯一产品基准是 `http://localhost:5207/#today`，当前架构以 [DONEGO-CANONICAL-ARCHITECTURE-2026-10-16.md](DONEGO-CANONICAL-ARCHITECTURE-2026-10-16.md) 为准。

日期：2026-09-13。状态：全部待审批。主稿为 [PRD-V3](PRD-V3.md)，依据为 [差距地图](V3-GAP-MAP.md) 与 [市场研究](V3-MARKET-RESEARCH.md)。

## 建议你批准的整体方向

下一大版本把 Tango Done&Go 做成一套能处理真实责任冲突的个人时间与行动协调层：**真实数据 → 有代价的选择 → 有限授权 → 外部结果核验 → 保持安静**。优先把现有产品骨架变为跨设备、可恢复、可解释的真实系统；双人协商和持续授权分阶段审批。

不是再做一套视觉概念，也不是同时扩张成任务、笔记、会议、团队与全能代理。默认瓷白、水墨开关、18 屏信息架构和 Tango Done&Go 品牌保留。

## D01：下一版本的价值单位

推荐：以一次“本人想保留的时间受到真实责任影响”的边界事件为核心。用户能减范围、改方法、调安排、准备协商、接受代价或保持原状。完成后不再追加普通提示。

代价：不会先补齐市场上所有任务/项目管理功能；一开始适合有一定调整空间的用户，而非所有日历用户。

替代：做通用 AI 任务日历。能力更容易被理解，但与成熟产品高度重叠，会削弱责任/授权/不行动权的差异化。

需要你的判断：是否批准这一核心定位？如果否，应明确首要情境，不能让后续模块同时服务多个相互冲突的目标。关联 PRD 第 1–2 节、H1/H2。

## D02：P0 是否包含服务端业务数据与跨设备

推荐：包含。保留当前 React/Vite + Node + SQLite 单机模块化架构，把业务权威写入迁到服务器，浏览器只作缓存/私人离线草稿；旧数据需本人确认归属并可恢复迁移。

代价：数据迁移、所有权、冲突和队列恢复会成为前期主要工作，页面新增速度不会代表进度。

替代：先保持单设备本地。可以缩短技术路径，但必须明确产品只在该浏览器保存业务数据，不能宣称多设备连续使用；这与“多人账号长期可用”的期待有明显差距。

需要你的判断：是否接受先打牢这一 P0 基础？推荐批准。关联 V3-04–06、20、37–40。

## D03：首个真实日历，是 Google 还是继续 Apple

推荐的工程候选：Google Calendar，一个账号、选定本人主日历，先读后按需写，仅 Tango Done&Go 创建的私人“不可用”块；不改旧事件、不加参会人、不发会议邀请。官方接口和自定义 ID 适合有界服务端执行与对账，但需要实际 OAuth/配额/用户覆盖验证。

重要历史约束：早期产品已选择 Apple Calendar。Google 是本次提出的先后顺序建议，**不是对既有方向的自动替换**。如果你本人及首批试用者以 Apple 为核心，应选 Apple，先验证 EventKit/CalDAV、运行环境和多用户权限；本轮 Apple 技术研究不足，不能虚构与 Google 同等证据。

两者共同边界：P0 只做一个连接器；连接器写入的日历块不等于操作系统静音，也不等于其他人不能安排会议。副日历与主日历 availability 的效果必须实测，不能在 UI 上笼统写“保护成功”。

需要你的判断：选 Google 优先，还是 Apple 优先？这是最影响实施路径的待定项。关联 V3-23–25、研究 S21–S22。

## D04：多人能力分三阶段

推荐：P0 做多个隔离账号的可靠个人闭环；P1 增加双人请求/拒绝/反提案/相同条款同意；P2 才增加有期限、资源和预算边界的持续授权与家庭/团队。

代价：首次 V3.0 不自动向另一人发协商或改会议。可以先生成私人建议草稿，由本人在原工具处理。

替代：P0 同时做协作和自动化。会叠加收件者身份、最小共享、协议版本、各自授权和部分执行，显著扩大失败影响与审阅范围。

需要你的判断：是否批准分阶段边界，而不是把 P1/P2 当作本次实施清单？关联 V3-44–48。

## D05：本地部署的可靠性目标

推荐：继续本机服务经 Cloudflare tunnel 访问；应用/worker/connector 托管启动、备份加密、恢复演练、健康与回滚有证据。拟议 RPO ≤24h、RTO ≤4h，验证后才作为运营目标。

当前并行开发已新增容器文件，部署文档也描述 launchd；这些资产需要合并入后续现状复核，不在本轮 PRD 擅自切换宿主或上云。

代价：主机睡眠、断网、磁盘故障仍影响公网可用性；不承诺 24×7 商业 SLA。若需要真正持续可用，则需要另外批准常开专用主机或托管环境、预算与迁移方案。

需要你的判断：本地常开试用是否满足首版目标？没有新的托管批准时继续本地方案。关联 V3-40、G6。

## D06：隐私、保留与试用判断标准

推荐：模型处理明确展示来源范围/提供方/成本或未知；不默许个人资料画像；管理员配置端点不等于用户同意传输。建议个人内容保留至本人删除，技术日志 30 天、最小审计 90 天、加密备份滚动 7 天、在线删除目标 24h；恢复时应用删除标记。期限是待审产品参数，不是法律结论。

研究建议：8–12 人、2–3 周形成性试用，优先理解程度、主动监督成本、技术结果和本人认可。未回应保持未知；延期不算时间节省。先证明主闭环有价值，再定价和扩 P1。

代价：不能快速用“节省多少小时”“用户满意率”做缺少依据的宣传；删除/审计/恢复设计要协调具体保留范围。

需要你的判断：是否接受这组保留/透明性/试用基线，或指定更短期限与更小试用范围？关联 V3-27、31、36、38–39、第 8 节。
